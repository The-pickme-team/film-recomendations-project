# GitHub Flow

У цьому проєкті ми працюємо за спрощеним GitHub Flow із довготривалими гілками `main` та `dev`.

## Гілки

- `main` — стабільна гілка. У ній міститься лише перевірений код, готовий до релізу.
- `dev` — основна робоча гілка для інтеграції нових змін.
- `feature/{опис}` — короткочасна гілка для одного завдання або функції.
- `release/{версія}` — гілка підготовки релізу, де проводяться фінальна перевірка, доопрацювання та виправлення.

## Як працювати над завданням

1. Завжди створюй нову гілку від `dev`.
2. Назви гілки роби зрозумілими: `feature/login-page`, `feature/add-analytics`, `feature/fix-random-bug`.
3. В одній feature-гілці тримай одне логічне завдання. Якщо завдання велике, краще розбити його на кілька гілок.
4. Пиши код, регулярно синхронізуйся з `dev`, якщо вона встигла випередити.
5. Перед PR перевір код лінтером, форматером і тестами, якщо вони є.

## Коміти

- Коміти мають бути короткими та зрозумілими.
- Краще писати коміти в наказовому способі: `add: login form`, `fix: redirect bug`, `update: analytics parser`.
- Не поєднуй у одному коміті зміни, що не пов’язані між собою.
- Якщо можливо, роби коміти невеликими та логічними, щоб їх було легко читати та скасовувати.

## Merge request / Pull request у `dev`

- Після завершення роботи створіть PR з `feature/{...}` у `dev`.
- Бажано не зливати зміни безпосередньо без PR, якщо це не терміновий технічний фікс.
- Перед злиттям перевір:
    - код компілюється і проходить перевірки;
    - немає конфліктів з `dev`;
    - зміни дійсно стосуються одного завдання;
    - опис PR пояснює, що зроблено і як це перевірити.
- Кращий спосіб злиття — `squash merge`, якщо історія комітів у feature-гілці не потрібна окремо.

## Підготовка релізу

1. Коли в `dev` накопичилося достатньо готових функцій, створюється `release/{версія}` з `dev`.
2. У релізній гілці вносяться лише фінальні правки: виправлення помилок, доопрацювання, оновлення версії, документації тощо.
3. Нові функції до релізної гілки не додаються.
4. Після перевірки `release/{версія}` зливається в `main` через PR.
5. Після злиття в `main` зміни з реліз-гілки потрібно повернути назад у `dev`, щоб гілки не розходилися.

## Правила для `main`

- `main` завжди має залишатися стабільним.
- Ніяких прямих експериментів та незавершених фіч у `main`.
- Будь-який hotfix спочатку оформлюється акуратно, а потім повертається в `dev`, щоб виправлення не загубилося.

## Коротко

- Працюємо з `dev`.
- Нове завдання — нова гілка `feature/{...}`.
- Закінчив роботу — PR у `dev`.
- Накопичили зміни — `release/{версія}`.
- Перевірили реліз — PR у `main`.
- Після релізу синхронізуємо `dev`
