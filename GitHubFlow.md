# GitHub Flow

В этом проекте мы работаем по упрощенному GitHub Flow с долгоживущими ветками `main` и `dev`.

## Ветки

- `main` - стабильная ветка. В ней лежит только проверенный код, готовый к релизу.
- `dev` - основная рабочая ветка для интеграции новых изменений.
- `feature/{описание}` - короткоживущая ветка для одной задачи или фичи.
- `release/{версия}` - ветка подготовки релиза, где проводятся финальная проверка, полировка и фиксы.

## Как работать над задачей

1. Всегда создавай новую ветку от `dev`.
2. Имя ветки делай понятным: `feature/login-page`, `feature/add-analytics`, `feature/fix-random-bug`.
3. В одной feature-ветке держи одну логическую задачу. Если задача большая, лучше разбить ее на несколько веток.
4. Пиши код, регулярно синхронизируйся с `dev`, если она успела уйти вперед.
5. Перед PR проверь код линтером, форматтером и тестами, если они есть.

## Коммиты

- Коммиты должны быть короткими и понятными.
- Лучше писать коммиты в повелительном наклонении: `add: login form`, `fix: redirect bug`, `update: analytics parser`.
- Не смешивай в одном коммите несвязанные изменения.
- Если возможно, делай коммиты маленькими и логичными, чтобы их было легко читать и откатывать.

## Merge request / Pull request в `dev`

- После завершения работы создай PR из `feature/{...}` в `dev`.
- Желательно не мержить изменения напрямую без PR, если это не срочный технический фикс.
- Перед мерджем проверь:
	- код собирается и проходит проверки;
	- нет конфликтов с `dev`;
	- изменения действительно относятся к одной задаче;
	- описание PR объясняет, что сделано и как это проверить.
- Предпочтительный способ мерджа - `squash merge`, если история коммитов в feature-ветке не нужна отдельно.

## Подготовка релиза

1. Когда в `dev` накопилось достаточно готовых фич, создается `release/{версия}` от `dev`.
2. В release-ветке делаются только финальные правки: багфиксы, полировка, обновление версии, документации и т. д.
3. Новые фичи в release-ветку не добавляются.
4. После проверки `release/{версия}` мержится в `main` через PR.
5. После мерджа в `main` изменения из release-ветки нужно вернуть обратно в `dev`, чтобы ветки не расходились.

## Правила для `main`

- `main` всегда должен оставаться стабильным.
- Никаких прямых экспериментов и незавершенных фич в `main`.
- Любой hotfix сначала оформляется аккуратно и затем возвращается в `dev`, чтобы исправление не потерялось.

## Коротко

- Работаем от `dev`.
- Новая задача - новая `feature/{...}` ветка.
- Закончил работу - PR в `dev`.
- Накопили изменения - `release/{версия}`.
- Проверили релиз - PR в `main`.
- После релиза синхронизируем `dev`.
